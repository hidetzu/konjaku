# 配るデータの重さに上限を置き、機械で見張る

- 状態: 採用
- 日付: 2026-08-14

## 何が問題だったか

ピンを10件に増やし、9つの街の建物を取り込んだ。**取ってみたら、配れない量だった。**

豊洲だけのときは z14 タイル1枚が 730KB で、「いちばん重いタイルで gz 218KB」と記録してあった。
**上野・西新宿・渋谷が桁違いに濃く、豊洲で決めた「z14 タイル1枚＝1ファイル」がそのままでは持たなかった。**
スマホで 3D を開くたびに gz 1.9MB を引かせることになっていた。

**1地点で決めた設計が、10地点で破れる。** しかも破れたことは画面に出ない。

## 何を測ったか

```
取り込み                    64タイル / 403,397件
生の合計                    118.9MB
いちばん重い z14 タイル1枚    5.25MB（gz 473KB）
/peel 1画面（z14 を最大4枚）  生 約20MB / gz 約1.9MB
```

詰めた後:

| | そのまま | 詰めた後 | |
|---|---|---|---|
| 生 | 118.9MB | **17.0MB** | 7.0倍 |
| gz | 12,193KB | **4,838KB** | 2.5倍 |
| いちばん重い1枚（gz） | 473KB | **199KB** | 2.4倍 |

3D 1画面（4枚）で gz 1.9MB → **約800KB**。同じ画面が読む MapLibre 本体が 1,032KB なので、同じ桁に収まった。

そして詰め直しの検算が実際に誤りを捕まえた ―― **63.05m → 63.1m**。
0.1m 刻みの丸めとして正しい差だが、**確かめずに書いていたら「たぶん合っている」で40万件を書き換えていた。**

## 決めたこと

- **1枚 250KB を上限**にする（いま 199KB）。目安は「**建物4枚で MapLibre 本体を超えない**」
- 濃い土地を足すとまた静かに超えるので、**機械で押さえる**
- **詰め方の定義は1か所**（`scripts/bl-format.mjs`）。取り込みと詰め直しの両方がここを使う（0021）
- **詰め直しは、戻して確かめてから書く。** 1枚ごとに「詰める→戻す→元と全点比較」を通してからしか書かない
  （座標 1e-5度、高さ 0.05m を許容の上限）
- **捨てるのは、どこも読んでいないものだけ。** `name` と `id` は `grep` で確認してから配布データから外した。
  ⚠ 捨てたのは配るデータからで、OSM から取るのをやめたわけではない
- 高さの刻み（0.1m）は**新しく粗くしたのではなく、画面が元から `Math.round(h*10)/10` で出していた刻みに合わせた**だけ

## そうしなかったこと

- **取り込みを途中で止める** … Overpass に二度同じことを訊きたくないし、
  **取ったファイルそのものが生データ**なので、詰め方は手元だけで直せる。最後まで走らせた
- **タイルを分割して枚数を増やす** … 0002 の試算（全国で約10万ファイル）に当たる
- **「たぶん大丈夫」で書き出す** … 40万件は目視で確かめられない

## これを守っているもの

- `scripts/bl-format.mjs`（唯一の定義）、`scripts/pack-buildings.mjs`（戻して確かめてから書く）
- `npm run check` の `建物のタイル 64 枚、いちばん重い1枚が gz 199KB（上限 250KB／合計 4838KB）` /
  `建物の詰め方が、書く側と読む側で一致（313 件で照合）`
- `npm run render` の `取り込んだだけの土地でも、3D が静的で成り立つ`
  （**豊洲は事前計算の bbox を持つ唯一の土地**なので、豊洲が通っても他が通る証明にならない。広島で1つ通す）
- `scripts/cost.mjs` — 1人あたりの通信を数える
