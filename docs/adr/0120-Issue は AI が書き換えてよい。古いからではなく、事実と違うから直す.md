## ⚠ 滞留の実測（2026-10-11）

```text
閉じた Issue 106 件の滞留日数
  中央 0 日 ／ 最大 17 日
  1 日以内 74 件（70%）／ 7 日以内 92 件（87%）／ ⚠ 30 日超 0 件
```

## ⚠ 世の中ではどうしているか（2026-10-11 に Web 検索で調べた）

### ⚠ 自動で閉じる（stale bot）は批判が強い

```text
時間だけで閉じると、⚠ 有用な文脈が消える（⚠ 維持者が対処する価値を認めた issue も失われる）
「沈黙 = 価値が低い」ではない（⚠ 複雑な case は再現と文脈が要るから残っている）
triage の問題を解決せず、⚠ 隠すだけ（⚠ 大量に閉じて見た目を綺麗にする）
bot が貼った stale ラベルを維持者が外し、⚠ bot が再度貼る、という循環が起きる
```

⚠ **「Issue を開いたまま無視してよい」と理解する維持者が増えている**という指摘もあった。

### triage の慣行は「時間を確保する」

⚠ **週次または日次の triage 時間を確保する。**⚠ **担当を回す。**
⚠ **ただし、⚠ これは OSS で外部から Issue が来る前提。**
⚠ **今昔は個人開発＋AI で、⚠ Issue は Owner か AI が作り、⚠ open は 6 件。**⚠ **規模が違う。**

### ⚠ 「部分修正後に説明が古くなる」問題は実在する（⚠ ただし確立した慣行ではない）

⚠ **同じ問題の記録はあった**（⚠ 「review-fix のあと drift check が無く、文書が head と矛盾する」）。
⚠ **提案されているのは review サイクルに drift check を足すこと。**
⚠ **ただし検索で出たのは AI が生成したリポジトリの Issue が大半で、⚠ 業界の定番ではない。**
⚠ **「同じ問題に当たっている記録」として扱う。**

## 決めたこと

⚠ **AI が Issue を書き換えてよい。**⚠ **規則は [`CLAUDE.md`](../../CLAUDE.md) §7-3。**

```text
外す    gh issue edit            ⚠ AI が書き換えてよい
残す    gh issue close           ⚠ 閉じるのは人
残す    --add-label ready-for-ai ⚠ 付けるのは人（CLAUDE.md §7-2）
```

### ⚠ 核心は「古いから直すのではない」

⚠ **時間を理由に触らない。**⚠ **事実と違うから直す。**

⚠ **これは stale bot の批判への答えでもある。**⚠ **あちらが有害なのは「時間だけで判断する」から。**
⚠ **こちらは「実測で確かめたことだけ直す」。**⚠ **測っていないなら触らない。**

⚠ **だから「一定期間で見直す仕組み」は採らなかった**（⚠ Owner の当初の問い）。
⚠ **期間で見ると、⚠ 事実と合っているものまで触る理由ができてしまう。**

### ⚠ 消さない

⚠ **追記で直す**（⚠ なぜそう書いたかが読めなくなる）。
⚠ **訂正したことを本文に書く**（⚠ いつ・何を・どの実測で）。
⚠ **`Goal` / `Scope` / `Out of Scope` / `Owner Decisions` は触らない**（⚠ 人が決めたこと）。

## 何を見張るか

⚠ **`test/check/guard.mjs`「人の判断を飛ばさない」。**
⚠ **判定の字からも「書き換える」を外した**（⚠ **見ていないものを名乗らない**。`CLAUDE.md` §1）。

⚠ **境界を 3 通りで確かめた**（2026-10-11。⚠ `.md` のコード枠に書いて `npm run check`）:

```text
gh issue edit                → ⚠ 落ちない（⚠ 外した）
gh issue close               → ✗ 落ちる
--add-label ready-for-ai     → ✗ 落ちる
```

⚠ **書き換え方そのものは、⚠ 機械で見張れない**（⚠ 「事実と違うか」は内容の判断）。
⚠ **規則で縛るだけ**（`CLAUDE.md` §7-3）。⚠ **そう分かったうえで運用する。**

## ⚠ 追記（2026-10-11。⚠ **追記の書式を決めた**）

⚠ **Owner の指摘**: ⚠ **「消さない。追記で直す」は open 6 件なら十分だが、
⚠ 長期間残る Issue では訂正が積み重なって、⚠ 現在の事実がまた読みにくくなる。**

⚠ **仕組みは増やさない。**⚠ **書式だけ決めた**（`CLAUDE.md` §7-3）。

```text
本文      ⚠ 当時の記録（⚠ 触らない）
Updates   ⚠ 現在との差分（⚠ 新しいものを上に積む）
```

⚠ **`Updates` は本文の該当箇所を名指す。**
⚠ **名指さないと、⚠ 読む人が本文を信じてしまう**（⚠ どこが古いのか分からない）。

## ⚠ この境界が何を分けているか（⚠ Owner の言葉。2026-10-11）

```text
AI    ⚠ 事実の保守をしてよい
人    ⚠ 仕事の意味・優先順位・終了を決める
```

⚠ **`ready-for-ai` を AI に付けさせない判断が、⚠ ここで効いている。**
⚠ **「Issue を書ける」と「AI 自身が着手可能だと認定できる」は別。**

## ⚠ 追記（2026-10-11。⚠ **いつ見るかを決めた**）

⚠ **Owner の指摘**: ⚠ **「気づいたら直せる」だけでは、⚠ いつ気づくかが決まっていない。**

⚠ **時間では決めない**（⚠ この ADR の核心）。⚠ **作業の節目で見る。**

```text
issue-ready §4-2    ⚠ 着手する 1 件の本文が、⚠ 現状と合っているか
change-review §5    ⚠ 部分修正で、⚠ その PR が触る Issue の本文が古くなっていないか
```

⚠ **`loop-controller` は触っていない。**⚠ **あれは判断基準を持たない設計で、
⚠ READY_CHECK が必ず `issue-ready` を通す**（⚠ 「本文はラベルを付けたあとに変わる」と
既に書いてあった）。⚠ **だから正本を 1 か所に置けた。**

### ⚠ 他の open な Issue は見ない（Owner 判断）

⚠ **実測（2026-10-11）**: ⚠ **hidetzu/konjaku#475 は 36 日間、⚠ 誰も読まなかった。**
⚠ **その間、害は出ていない。**⚠ **害が出たのは「次に進めようとして本文を信じかけた」瞬間。**

⚠ **読まない Issue が古くても害は出ない。**
⚠ **「他の open も見る」にすると、⚠ 読む予定のないものまで確かめることになり、
⚠ 定期棚卸しを作業の節目に貼り替えた形に近づく。**

⚠ **open が増えたら、⚠ そのとき決める**（⚠ いま 6 件。⚠ 閉じるものは当日に閉じている）。

### ⚠ これでも埋まらない穴

⚠ **`loop-controller` を回さない Issue は、⚠ やはり誰も見ない。**
⚠ **hidetzu/konjaku#475 は `ready-for-ai` が付いていなかったので、⚠ この節目に掛からない。**
⚠ **つまり、⚠ この追記を入れても hidetzu/konjaku#475 は救えなかった。**

⚠ **救うには「`ready-for-ai` を付けるときに本文を確かめる」が要るが、⚠ それは人の手順。**
⚠ **AI 側の仕組みでは埋まらない。**⚠ **そう分かったうえで、⚠ ここまでにしている。**
