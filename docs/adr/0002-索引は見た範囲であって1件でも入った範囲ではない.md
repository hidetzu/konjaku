# 索引が持つのは「このタイルを見た」であって「1件でも入った」ではない

- 状態: 採用
- 日付: 2026-08-14

## 何が問題だったか

書き出しの索引を `SELECT z14x, z14y FROM feature GROUP BY …` から作っていた。
取り込みは「中心から N km の矩形」で回していたので、**タイル境界と一致しない。**

結果、**1件が端に落ちただけのタイルが「全面を調べた」として索引に載っていた。**

そのタイルで画面はこう出していた。

```
「1936年までのあいだに、記録のある変化はありません。」
```

一度も見ていない地面について断定していた。しかも索引に載っているので Wikidata へ1回も出ない。
**通信断のときより静かに嘘をつく。** 0001 の掟を、いちばん奥で破っていた。

## 何を測ったか

```
索引タイルの実問い合わせ率   100% は 3/27 ／ 50%未満が 17/27 ／ 中央値 42.5% ／ 最悪 3.6%
表示枠 274枚のうち          問い合わせ率 100% 未満 183枚（67%）／ 0% が 33枚
```

直した後:

```
前  7地点 → 328件 / 27タイル（索引の意味＝「1件でも入った」）
後  7地点 → 769件 / 35タイル（索引の意味＝「このタイルを見た」）
    うち「調べて0件」のタイル 5枚 ← 以前は構造上ゼロだった
```

いま配っているもの: 事物 2,367件 / z14 87タイル（z12 20束）、建物 403,397件 / z14 64タイル。

同じレビューで、隣接する誤りも出た。

- **四隅の経緯度から z14 を出していた** … 枠の東端・南端が境界に乗ると、内側にかかっていない隣タイルを要求する。
  実測 **345枚中71枚（21%）** が、**既に持っているデータについて**「分かっていません」と言っていた
- **上限（LIMIT 800）の到達を検出していなかった** … 密な土地ほど、断定的に取りこぼす

## 決めたこと

- **取り込みを z14 タイル境界で回す。** 中心から N km の矩形ではなく、タイルを単位にする
- `coverage(z14x, z14y, at, n, truncated)` に「見た」という事実を記録し、**索引はそこから作る**
- **0件でもタイルを書く。** 「調べて0件」と「調べていない」を画面から区別できるようにする
- z14 の添字は z16 の添字から出す（`z14 = z16 >> 2`）。丸めが起きない
- 上限に当たったタイルは `truncated` として記録し、タイルにも書く。そこでは「無くなった」と言わない
- `coverage.layer` を分ける。`ev` の0件（年つきの事物が無い）と、別の層の0件は意味が違う

## そうしなかったこと

- **索引を消して、毎回 Wikidata に問い合わせる** … 索引の意味を直すほうが安い。全PVが外へ流れる形は 0011 と逆行する
- **「たぶん見た」で丸める** … これが元の実装だった
- **z14 の1タイル1ファイルを全国へそのまま広げる** … 検証者の試算で約10万ファイル・約1,400ディレクトリ、
  取り込み 41,997回・sleep だけで 17.5時間。**10万ファイル書き出してからでは戻せない**ので、
  先に z12 束ね（約6,200ファイル）へ倒した。事物はいま z12 束、建物は z14 のまま

## これを守っているもの

- `scripts/db.mjs` の `coverage` テーブル。`spec` 列も埋める（空のままだと再開判定が効かない）
- `scripts/export-tiles.mjs` — 「この範囲には何も無い」と「知らない」を混ぜない
- `npm run check` の `事物の索引と本体が揃っている` / `建物の索引と本体が揃っている` /
  `束はあっても、見ていない区画では答えない` / `上限に当たったタイルでは、消えたことにしない`
- `public/_headers` — 索引と束のキャッシュ寿命を揃える（0021 を参照。分かれると穴が復活する）
