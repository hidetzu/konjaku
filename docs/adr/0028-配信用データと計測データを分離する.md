# 配信用データと計測データを分離する

- 状態: 採用
- 日付: 2026-08-16

⚠ 2026-08-16 時点の構成を記録する。

## 判断

地図表示に使う地理データは Cloudflare Workers Assets で静的に配信し、
D1 は利用状況・依存サービスの状態を集計する計測用途に限定する。

Wikidataの事物情報、OSM建物の取り込み途中データ、取得範囲、再生成に必要な状態は、
まずローカル SQLite（`.data/konjaku.db`）で管理する。公開時に生成したファイルと索引を
Workers Assets に配置し、`public/data/assets.json` を各レイヤーの参照契約とする。

## データの流れ

```text
国土地理院 / OSM / Wikidata
          ↓ 取り込み・検証
ローカル SQLite（事物・建物の取り込み作業用）
          ↓ export / pack
public/data/（配信用ファイル）
          ↓ deploy
Cloudflare Workers Assets ──→ ブラウザが索引・タイルを読む

ブラウザの匿名イベント
          ↓ /t
Worker ──→ D1（集計）
```

## Workers Assets に置くもの

利用者が地図を表示するための、読み取り中心の公開データを置く。

- 建物の索引と z14 タイル（`data/bl/`）
- 明治期の水域・土地情報とその索引
- 写真・年代情報のタイル
- 地形分類などの判定用静的データ
- トップ画面の候補地
- `assets.json`（レイヤー、形式、索引、本体、出典、生成時点）

これらは CDN キャッシュを利用でき、地図表示のたびに Worker や D1 を経由しない。
索引と本体は同じ公開物として生成・デプロイし、未整備範囲を「データなし」と
誤って扱わないよう、索引には実際に確認した範囲だけを載せる。

## D1 に置くもの

現時点の D1 は計測専用である。

- `tick`: 判定、共有、保存、年代操作、3D表示などの日別件数
- `health`: 地形分類、明治期データ、標高、写真などの依存先ごとの成功・失敗件数

計測には地名、緯度・経度、Cookie、利用者識別子、個別の閲覧履歴を保存しない。
地図データをD1から都度検索する用途には使わない。

## ローカル SQLite の位置づけ

`.data/konjaku.db` は公開APIのDBではなく、事物・建物の取り込みと配信物生成のための
作業用DBである。事物、建物、タイルごとの coverage、取得条件、取得日時、
取り込み履歴などを持つ。
一方、水域のGeoJSON、地形分類、写真、候補地などは、それぞれの生成スクリプトが
外部データやseedから直接 `public/data/` に書き出しており、現状はこのSQLiteを経由しない。
このDBの内容をそのまま本番のD1へ移行することは、現在の構成では行わない。

## 将来D1へ追加できるメタデータ

管理画面や自動公開処理が必要になった場合に限り、次のような運用メタデータをD1で管理できる。

- アセットの公開バージョンと生成日時
- 外部データの取得日時・出典・チェックサム
- 範囲やタイルの生成成功・失敗状態
- 再生成が必要かどうか

これは配信用ポリゴン本体をD1に置くことを意味しない。公開データは引き続き
Workers Assetsを正とする。

## 変更時の確認事項

- 新しい地理レイヤーは、まずAssetsで静的配信できるか検討する
- D1へ追加する場合は、表示データではなく動的・集計・運用メタデータか確認する
- `assets.json`の形式、索引、本体、出典、生成時点を同時に更新する
- `npm run check`で索引と配信ファイルの対応を確認する
- D1の計測項目を変更する場合は、保存する情報が匿名集計の範囲を超えないことを確認する
