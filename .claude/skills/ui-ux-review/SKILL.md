# UI/UX Review

UI を設計・変更するときは、実装者ではなく初見の利用者として判断する。

⚠ **この Skill は新しい UX 方針を作らない。**
基準は [`docs/SPEC.md`](../../../docs/SPEC.md)・[`docs/adr/`](../../../docs/adr/)・
[`CLAUDE.md`](../../../CLAUDE.md)・Issue の Owner Decisions にある。
⚠ **価値判断が要るものは `HUMAN-DECISION` に回す。**自分で決めない。

---

## 0. ⚠ 先に測る。要約を読んで書かない

⚠ **要約を読むだけでは指摘が出ない。**画面を開いて、押して、px で測る。

```
npm run serve            手元で開く
```

⚠ **測る幅は 4 つ。**別の幅の数字を持ち込むと、その数字自体が嘘になる。

| 幅 | 何の代表か |
|---|---|
| **375×667** | ふつうのスマホ。⚠ **ここが基準** |
| **344×882** | ZFold5 のカバー画面。⚠ **窮屈が最初に出る** |
| **320×640** | いちばん狭い。⚠ **縦も足りなくなる** |
| **1280×800** | PC |

⚠ **見えているかは `checkVisibility()` で見る。**
`getBoundingClientRect()` は、閉じた `<details>` の中で**直前の寸法を返し続ける**
（`content-visibility:hidden`。実際に 268×38 と読めた）。

## 1. 7 原則

1. **5秒ルール** — 初見から 5 秒以内に「この画面で何ができるか」が分かる
2. **主役は1つ** — 画面ごとに Primary Action を 1 つ。同じ強さで複数を目立たせない
3. **結論 → 詳細 → 根拠** — 最初に答え。技術的詳細は掘れる構造に
4. **説明より操作** — 「〜できます」を増やす前に、見て分かる形にできないか
5. **足す前に隠す** — 足す前に、既存を消す・まとめる・畳めないか
6. **Mobile First** — PC より先にスマホ幅。⚠ **Primary Action・結果・操作対象が最初に見える**
7. **初見として見る** — 「知っているから分かる」を判断根拠にしない

## 2. 今昔の掟（⚠ ここは 7 原則より上位）

⚠ **面白さより先に、情報が正しいこと。**見やすさのために、これを崩さない。

| 見るところ | ⚠ 落ちる例 |
|---|---|
| **取れなかった ≠ 無い** | 「データがありません」と書いて、実は読めなかっただけ |
| **推定を実測のように見せない** | 確率・確信度を出す／実測でない数字を書く |
| **分母** | 別の範囲の数字を並べる（⚠ 名古屋 1.7%＝**面積** と 豊洲 99.6%＝**建物**） |
| **内部状態を出さない** | `NO_RECORD` `UNKNOWN` `未対応` をそのまま画面へ |
| **できないことから書き始めない** | ⚠ 先に「ここで何ができるか」。⚠ **限界は消さず、順番と主語を変える** |
| **進行形を状態の説明に使わない** | 「取得中」「届いていない」は、いま自分の端末で起きていることに読める |
| **`⚠` を在庫の話に使わない** | ⚠ は危険（災害リスク）に使っている。混ぜると「危ない土地」に読まれる |
| **押しても何も起きない導線を置かない** | ADR 0026 |

## 3. 測って見るところ

| 何 | 基準 | ⚠ どう測るか |
|---|---|---|
| **タップの的** | **44×44px 以上** | `getBoundingClientRect()`。⚠ 指の端末だけ |
| **Primary Action** | 1 つ。一言で言える | 言えなければ NEEDS-FIX |
| **最初に見える情報** | 結論 | 画面上端から、答えの行までの y |
| **横あふれ** | **0** | `scrollWidth > clientWidth` を `documentElement` と各段で |
| **重なり** | **0** | 隣り合う要素の矩形。⚠ **同じ積み上げに入れる。固定値で避けない** |
| **画面中央を覆う量** | 調べている地点（`/peel` は y=画面高/2）を覆わない | 板の上端 y と中央の y |
| **情報量** | ⚠ **増えたら、何を減らしたか言う** | 要素数・説明文の字数を前後で |
| **視線順序** | 上から結論 → 詳細 → 根拠 | DOM 順と見た目の順が食い違っていないか |
| **実際の操作** | ⚠ **押す。畳む。開く。** | 押した結果が**同時に見えている**か |

⚠ **磨くより先に測る。**直す前に、いまどうなっているかを px と件数で出す。
⚠ **違う状態どうしを比べて「良くなった」と言わない**（現在 294px と 明治期 342px を
比べて改善と書いた実例がある）。
⚠ **測った字は捨てない。**4 幅・状態ごとに拾った文面と数字を、そのまま §4 で使う。

## 4. ⚠ 同じことを、何度も言っていないか

⚠ **これは lint ではない。**同じ語・同じ数字が 2 回出ること自体は不合格ではない。
⚠ **役割が違えば、重なっていてよい。**
⚠ 逆に、**字が違っても、利用者から見て同じ意味・同じ責務なら指摘する。**

§3 で拾った**画面の字そのもの**（4 幅・状態ごと）を並べて、5 つの目で見る。

| 何を見るか | ⚠ どう見るか |
|---|---|
| **1. 文言の重複** | 同じ説明が 2 か所以上に出ていないか |
| **2. 意味の重複** | 表現が違うのに、利用者には同じことを言っていないか |
| **3. 数字と分母の重複** | 同じ母数・同じ割合が繰り返されていないか。⚠ **その数字が「利用者の答え」なのか「根拠・データ品質」なのか**を分ける |
| **4. 用語の揺れ** | 同じ・近い概念に別の語を当てていないか。⚠ **意図した使い分けなら、問題なしとする** |
| **5. 責務の重複** | HUD・答えの板・押した結果・詳しい説明が、⚠ **同じ情報をそれぞれ持っていないか** |

⚠ 用語の揺れの実例（⚠ **同じ画面に並んでいた語**。2026-08-21・`main` = `484629c`・`/peel` で実測）:
**演出／推定／概算**、**地表／足元**、**水域／水面／旧水部**。
⚠ **並んでいること自体は不合格ではない。**使い分けているなら**その理由**を、していないなら**正本**を言う。

⚠ **「重なっている」で止めない。**どこを正本にし、どの段に置くかまで言う。

| 段 | 意味 |
|---|---|
| **常時** | 操作しなくても要る |
| **操作したとき** | 押した・動かしたときだけ要る |
| **ドリルダウン** | 開いて読めば足りる |
| **削除候補** | ⚠ **その画面から消せる。**⚠ ただし**事実そのものを消すのではない**（掟 §1）。⚠ 消すなら、どこで読めるかを同時に言う |

⚠ **なぜ同じ意味・同じ責務だと判断したかを、必ず書く。**書けないなら出さない
（⚠ 書かずに出すと、意図した使い分けまで「揺れ」として潰す）。

出す形（1 件ごと）:

```
[意味・責務の重複]
概念:  <利用者から見た 1 つのこと>
出現:  <UI 領域> — <実際に出ている字。⚠ 測った字をそのまま>
判断:  <なぜ同じ意味・同じ責務だと言えるか>
正本:  <どこを正本にするかの候補>
段:    常時 / 操作したとき / ドリルダウン / 削除候補
```

例（⚠ **実測** 2026-08-21・`main` = `484629c`・`/peel`・375×667・渋谷・SW 無効。⚠ 字は画面から写した）:

```
[意味・責務の重複]
概念:  建物データの母数と精度
出現:  HUD の補足   — 「建てられた年が分かるのは 23 / 5017 件だけ。高さも 3642 / 5017 件が推定です」
       答えの板     — 「4785 / 5017件の足元を判定」
       いま出ているもの — 「OSM に高さが入っているのは 1375 / 5017 件」「階数から換算したものが 190 件、
                          残る 3452 件は…こちらで立てた値」
       判定の結果   — 「建物 5017 件を判定しました」
判断:  4 か所とも**同じ母数（5017）**の精度の話で、
       ⚠ 利用者の問い（この土地は何だったか）そのものには答えていない。
       ⚠ 分母は同じなので「分母の食い違い」ではない。⚠ **責務の重複**として見る。
正本:  データ品質は、開いて読む側へ 1 か所に集める
段:    HUD は削除候補（⚠ 年代を動かすのに要らない）／ 答えの板は結論だけ ／ 残りはドリルダウン
```

⚠ **重複そのものは、原則 `Non-blocking`。**
⚠ ただし**分母の違う数字が同じ強さで並んでいる**ときは `Blocking`（§2 の「分母」）。
⚠ **どちらを正本にするかが割れたら `HUMAN-DECISION`。**言葉と優先順位は自分で決めない。

## 5. 判定を返す

```
Verdict: PASS / NEEDS-FIX / HUMAN-DECISION

Measured:
  <幅>  <何>  <実測値>          ⚠ 測っていないことは書かない

Blocking:
  - <掟に反する／操作が成立しない>

Non-blocking:
  - <直すとよいが、この変更を止めるほどではない>

Human Decision:
  - <見せ方の方針・言葉の選択・優先順位>
```

| 判定 | いつ |
|---|---|
| **PASS** | 掟に反しておらず、4 幅で操作が成立している |
| **NEEDS-FIX** | ⚠ **掟に反している**／44px を割っている／重なっている／横あふれ／押しても何も起きない |
| **HUMAN-DECISION** | ⚠ **どちらが良いか**の話になった。方針・言葉・優先順位。⚠ **自分で決めない** |

⚠ **Blocking が 1 つでもあれば PASS にしない。**
⚠ **測っていないことを「確認済み」と書かない。**測れなかったなら、そう書く。

## 6. ⚠ 迷ったら利用者に聞く

見せ方に迷ったら、**画面だけを見せて**確かめる。
⚠ **実在の利用者ではない**ので、そう明記する（例: 「利用者役 3 名に画面だけを見せた」）。

⚠ **人数と、何人がどう答えたかを書く**（「3/3 が『自分の通信のせい』と読んだ」）。
⚠ **読み方が割れたら、それ自体が結果。**多数決で消さない。

`AskUserQuestion` を使うと Slack にも飛ぶ（`.claude/hooks/ask-slack.mjs`）。
