# Change / Scope Review

⚠ **`git diff` を自分で読み直す。**要約や記憶で書かない。

⚠ **見せ方（画面）は見ない。**それは [`ui-ux-review`](../ui-ux-review/SKILL.md)。
⚠ **検査を回すのもここではない。**それは [`verify`](../verify/SKILL.md)。
ここが見るのは **変更そのものが、頼まれた範囲と掟の中にあるか**。

⚠ **基準を新しく作らない。**[`CLAUDE.md`](../../../CLAUDE.md)・
[`docs/SPEC.md`](../../../docs/SPEC.md)・[`docs/adr/`](../../../docs/adr/)・
Issue の Owner Decisions が正。

---

## 1. 何を読むか

```bash
git diff main...HEAD          # 変更そのもの
git diff --stat main...HEAD   # どこが動いたか
git log --oneline main..HEAD  # 理由ごとに分かれているか
```

⚠ **`--stat` だけで判断しない。**中身を読む。

---

## 2. 範囲

| 見るところ | ⚠ 落ちる例 |
|---|---|
| **Acceptance Criteria** | ⚠ **1 項目ずつ**、何で確かめたかと一緒に。⚠ 「たぶん満たしている」は満たしていない |
| **Out of Scope / Non-goals** | その外のファイルが動いている |
| **1 PR = 1 つの理由** | ⚠ 別の作業を巻き込んでいる（`git add -A` の事故） |
| **頼まれていない機能** | Issue に無いものが増えている |
| **不要なリファクタ** | 目的に関係ない書き換え |

---

## 3. 掟

⚠ **ここは範囲より上位。**範囲内でも、ここに触れたら `NEEDS-FIX`。

| 見るところ | ⚠ 落ちる例 |
|---|---|
| **取れなかった ≠ 無い** | 読めなかっただけなのに「ありません」と書く |
| **データにない ≠ 現実にない** | 資料の範囲外を、事実のように出す |
| **推定を実測のように見せない** | 確率・確信度／実測でない数字 |
| **分母** | 数字に**主張範囲の分母・測定日・測定条件**が無い。⚠ 別の範囲の数字を並べる |
| **同じ問いに答える実装を 2 つ** | ⚠ 同じ判断が 2 か所。⚠ **やむを得ないなら機械で突き合わせているか** |
| **データの意味を変えていない** | 分類・語彙・件数の数え方が変わっている |
| **内部状態を画面に出さない** | `UNKNOWN` `未対応` がそのまま |
| **押しても何も起きない導線** | ADR 0026 |

---

## 4. ⚠ 非同期の結果の鮮度

⚠ **`await` / callback / event の古い結果が、⚠ いまの「場所・年代・選択」を書き換えていないか。**

⚠ **この画面は、待っているあいだに前提が変わる。**
地点を変える・年代を動かす・建物を押す・パネルを開くは、⚠ **待ち時間より速い。**
投げた時点の前提で書き戻すと、⚠ **利用者が選んでいないものが画面に出る。**

| 見るところ | ⚠ 落ちる例 |
|---|---|
| ⚠ **投げたときと、返ってきたときで前提が同じか** | 別の地点へ移ったあとに、前の地点の結果が板を書き換える |
| ⚠ **古い応答の追い越し** | 遅い応答が、⚠ **あとから来て新しい応答を上書きする**（速い順に着くとは限らない） |
| **タイマー・再描画の予約** | 条件が変わったのに `setTimeout` が生きている（⚠ `clearTimeout` していない） |
| **失敗と成功の順序** | 「取得できていない」を出したあとに古い成功が来る／その逆 |
| ⚠ **状態を書く場所** | 同じ状態を 2 か所から書いている（⚠ **どちらが最後か決まらない**） |
| **中断** | 中断したはずの取得が、⚠ **中断後に結果を書いている** |

⚠ **確かめ方は「読む」ではなく「入れ替える」。**
⚠ **遅らせて、順序を逆にして、実際に起きるか**を見る（`await` の前後に人為的な遅延を入れる／
先に投げたほうを遅く返す）。⚠ **「起きにくいから」で通さない。**

⚠ **これは見せ方の話ではない**（`ui-ux-review` ではない）。⚠ **出ている中身が、いまの選択と違う**という
正しさの話なので、掟 §1 に近い側に置く。⚠ **古い結果で書き換わったものは、
利用者から見ると「そう観測された」と読める。**

⚠ **直し方までは決めない。**世代印・識別子の突き合わせ・中断のどれを採るかは実装の判断。
⚠ **見るのは「守られているか」だけ。**守られていなければ `NEEDS-FIX`。

## 5. 後始末

| 見るところ | ⚠ 落ちる例 |
|---|---|
| **死にコード** | 使われなくなった関数・CSS が残っている |
| ⚠ **古いコメント** | ⚠ **コードより強く誤誘導する。**実測値・件数・ファイル名が古い |
| ⚠ **写したコメント** | 別のファイルへ写して、⚠ **数字が合わなくなっている** |
| **効果のない変更** | ⚠ 書いたが、何も変わらない（実測で確かめる） |
| **セットで直したか** | 実装 → 検査 → コメント → README → `docs/SPEC.md` |
| **裸の Issue 番号** | ⚠ リポジトリ名つきで書く（移行後は別のものを指す） |

⚠ **検証していないことを「確認済み」と書かない。**

---

## 6. 返す形

```
Verdict: PASS / NEEDS-FIX / HUMAN-DECISION

Scope:
  変更したファイル N 件 / 理由 M 個      ⚠ 実際に読んだ範囲だけ書く

Acceptance Criteria:
  1. <AC>  → <何で確かめたか>  ✅ / ❌ / ⚠ 未検証

Blocking:
  - <掟に触れる／範囲の外／AC を満たしていない／⚠ 古い結果がいまの状態を書き換えうる>

Non-blocking:
  - <直すとよいが、この変更を止めるほどではない>

Human Decision:
  - <仕様・UX・データの意味>
```

| 判定 | いつ |
|---|---|
| **PASS** | AC を全部満たし、範囲の外へ出ておらず、掟に触れていない |
| **NEEDS-FIX** | ⚠ **AC が 1 つでも欠けている**／範囲の外／掟に触れる／⚠ **古い結果が書き換えうる**／後始末が残っている |
| **HUMAN-DECISION** | ⚠ **仕様・UX・データの意味**を決めないと進めない。⚠ **自分で決めない** |

⚠ **Blocking が 1 つでもあれば PASS にしない。**
⚠ **AC に「⚠ 未検証」が 1 つでもあれば PASS にしない**（`NEEDS-FIX` か、
`verify` へ戻して測る）。
