# Issue から PR まで

引数は Issue 番号（`#` は付いていてもいなくてもよい）。番号が無いときは、
何番をやるか聞く。勝手に選ばない。

**各段の結果を出してから次へ進む。** 黙って通しで走らない。

---

## 1. Issue とコメントを取る

```bash
gh issue view <N> --json number,title,body,labels,state,assignees
gh issue view <N> --comments
```

- **コメントは全部読む。** 本文より**後のコメントが正**。
  作業中に Owner の判断が入ったとき、コメントにしか書かれていないことがある
- `state` が `CLOSED` なら、そのまま進めずに確認する

## 2. きまりを読む

```
CLAUDE.md          このリポジトリでの作業のきまり
docs/SPEC.md       いま何ができて、何をどこまで言えるか（「掟」の節）
docs/adr/          その判断になった経緯
```

Issue が触る範囲に関係する ADR があれば、それも読む。

## 3. Owner Decisions と Non-goals を抜き出す

Issue 本文の節から、次を**そのまま書き出して**確認する。

- **Owner Decisions** … 最優先。ここに書かれたことを独自判断で変えない
- **Non-goals** … この外へ変更を広げない
- **Acceptance Criteria** … 完了の判断はこれで行う
- **Constraints / UX / Data Semantics** … Issue 固有の制約

⚠ コメントで上書きされていたら、コメント側を採る。
⚠ 本文とコメントが食い違っていて、どちらが正か決められないときは**聞く**。

## 4. 計画を出す

実装の前に、次を短く出して**承認を取る**。

- 触るファイルと、それぞれ何をするか
- Acceptance Criteria の各項目を、**何で確かめるか**（どの検査／どう測るか）
- **Owner の判断が要る点**があれば、ここで先に出す
- 測ってから決めるべきことがあれば、先に測って数字を出す
  （CLAUDE.md「磨くより先に測る」）

見せ方に迷ったら、実装前に利用者に確認することも選択肢に入れる。

## 5. 実装

- 目的を満たす**最小範囲**。Issue に直接関係しない大規模リファクタリングをしない
- 既存のコードを読んでから書く。同じ問いに答える実装を2つ作らない
- 内部状態をそのまま画面に出さない。人が読める言葉にする
- コードを変えたら、**コメント・検査・`docs/SPEC.md` も一緒に**直す
  （古いコメントはコードより強く誤誘導する）

## 6. 検査

⚠ **回し方は [`verify`](../verify/SKILL.md) にある。**ここには書かない
（掟: 同じ問いに答える実装を2つ持たない。⚠ 2 か所に書くと、片方だけ古くなる）。

`verify` が持っているもの: 入口の一覧と実測の速さ ／ Inner Loop と Final Gate ／
⚠ **落ちたのがこちらの不具合か外部かの切り分け** ／ `PASS` `FAIL` `NOT-VERIFIED`。

この Issue の作業として、ここで果たすのは次の 2 つ。

- ⚠ **Final Gate まで通してから PR を出す。**Inner Loop で緑でも「通った」と言わない
- ⚠ **この Issue で直した不具合を、検査として残す。**
  同じことがもう一度起きたら止まる形にする。
  ⚠ **足したら、わざと壊して、本当に落ちることを確かめる**
  （⚠ 落ちた理由の文言が、狙った主張になっているかまで読む）

## 7. 自己レビュー

`git diff` を**自分で読み直す**。見るところ。

- Acceptance Criteria を**1項目ずつ**、何で確かめたかと一緒に確認する
- Non-goals の外へ出ていないか
- 数字を書いたなら、**主張範囲の分母**になっているか
- 「取れなかった」を「無い」と書いていないか。推定を実測のように見せていないか
- 消し忘れた死にコード・古いコメントが残っていないか

**検証していないことを「確認済み」と書かない。**

## 8. コミット

- Conventional Commits（`<type>(<scope>): <subject>`）
- **変更を出した理由ごとに分ける。** `git add -A` で他の作業を巻き込まない
- `main` に直接コミットしない。ブランチを切る（`<type>/<短い名前>`）
- 本文に、**なぜそうしたか**と**測った数字**を書く

## 9. PR

- **`git push` は、そのつど許可を取る。** 前に許可をもらっていても取り直す
- PR 本文は `.github/PULL_REQUEST_TEMPLATE.md` に沿って書く

- `Closes #<N>` を入れる
- **⚠ `外部リンク` の検査は PR ではスキップされ、`main` にマージされてから走る。**
  マージ後の CI も見る

## 10. 報告

Issue に `Completion Report` をコメントとして残す。
判断が要るものがあれば、**そこで止めて聞く**。勝手に決めない。

```
Summary                  何をしたか
Changed                  変えたもの
Verification Results     検査の結果
Remaining Issues         残したこと
Owner Decision Required  判断が要るもの
```
